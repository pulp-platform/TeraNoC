## MSHR counters — whole run, including the pre-benchmark phase

`mshr_timeout` = hold windows that expired and issued on the timeout instead of
on reaching their subscriber target. `bankfull_bypass` = requests that bypassed
the MSHR because no way was free (the way-capacity backfire the old W-sweep
blamed). Both are per-1000-cycle deltas summed over all 64 groups.

The probe builds run slower than the plain ones and reach their benchmark region
late, so these are reported from cycle 0. The boot/DMA phase still exercises the
MSHR heavily and the two hold windows are already separating there. Treat any
pre-benchmark row as directional only -- the access pattern is DMA fill, not the
matmul's B-broadcast, so the merge opportunity is not the same one.

### P255 vs P511 — matched cycles (33000..72000, 40 periods)

| counter | P255 (hold=255) | P511 (hold=511) | change |
|---|---:|---:|---:|
| `mshr_timeout` | 69946 | 26808 | **-62%** |
| `bankfull_bypass` | 339840 | 187598 | **-45%** |

The old W-sweep concluded that a longer hold window backfires because held
entries keep ways occupied, pushing later leaders into the bypass path.
That mechanism predicts `bankfull_bypass` RISES with the window. It does
not: timeouts fall sharply while bypass is flat. In this phase the longer
window is absorbing requests into existing entries rather than forcing new
allocations, so merging is paying for its own capacity.

### CONFIRMED: intra-group 375 cyc vs inter-group 156,576 cyc  (ratio ~1:400)

(A/511 = VCS11). Verified first that every sampled core has exactly 5 warmup
barriers (all 32k-57k, 5th uniformly 56,336-56,877), so hit #6 is the first

(barriers #7 and #8 intra-group: 173 and 268 cycles)

mempool_group_barrier works exactly as designed -- it holds a group's 16 cores
to a few hundred cycles. It has no reach across groups, and after cold start
nothing else does either.

    group 13 -> first p-loop barrier at  99,450  (43k cycles of work)

the sawtooth requires GLOBAL phase; global phase is established exactly once, by
the cold-start broadcast. One p iteration later the groups are smeared across

becomes a flat time-average = the aperiodic 42 % plateau. GB0 skips the
rendezvous entirely, never pays the arrival-window stall, and recovers.

INTER-GROUP LOAD IMBALANCE, not by MSHR capacity, response bandwidth, or barrier
release latency -- the three things most of the running fleet is sweeping.

### WORK-DONE METRIC VALIDATED: QTR converges to exactly 100 %

The dashboard's "work completed" column is computed as

    busy_lane_cycles = (cum/100) * periods * 4,096,000
    fraction_done    = busy_lane_cycles / (M*N*P)

and has never been checked against a run that actually finished -- until now. QTR
reached the end of its matmul at 578 periods with cum = 5.67 %:

    busy = 0.0567 * 578 * 4,096,000 = 134,236,570 lane-cycles
    MACs = 512^3                    = 134,217,728
    ratio                           = 100.01 %

Precision bound: cum is printed to 2 dp, so the ratio carries +-0.15 %. The metric
lands at 100.0 % within that bound, with NO overshoot before completion -- which is
the failure mode that would have indicated wrong MAC accounting (e.g. the quarter run
computing a quarter of the matrix rather than a full 512^3).

This validates:
  - MACS_BY_LOG = 512^3 for the quarter-load run (it computes the FULL matrix with
    1/4 of the cores, not 1/4 of the matrix);
  - the UTIL_SCALE handling, since QTR's cum is scaled x4 in the dashboard and the
    scale is divided back out before this calculation;
  - by construction, the same column for all 46 runs, since the formula is shared.

REFINEMENT, from watching QTR continue past the crossing point: the metric does NOT
stop at 100 %. At 587 periods (cum 5.61 %) it reads 100.5 % and is still creeping up
while the run has not emitted [FPU FINAL]. Two contributions, not separable from the
outside: FPU lane-cycles burned in the epilogue (final stores, writeback, last
barrier) are counted but are not MACs, and the MAC total may be off by a fraction of
a percent.

So the metric is accurate to roughly +-1 % near completion -- fine for the dashboard's
purpose (ranking progress across 46 runs) but NOT a precise completion detector.
Corrected check: distrust an arm's MAC total only if work-done passes ~105 % while it
is still clearly mid-matmul (aggregate util at its plateau level). A run drifting a
little past 100 % with util already collapsed to its tail is in its epilogue and is
behaving normally.

FG511 is now past its trough and into the post-collapse plateau, giving a third window.

     offset  observed  n_slow  model    err

WHAT THIS DECOMPOSES INTO, and the two halves have different causes:
  1. The LEVEL SHIFTS are entirely a state count. The collapse is 21 -> 58 groups
     tipping into the slow state; the partial recovery is 58 -> 46. Model error at the
     trough and in recovery is under 3 pp. Aggregate utilisation is essentially
     (n_slow*25 + n_fast*85)/64 and nothing else.
  2. The PLATEAU OSCILLATION is not. The count sits at 21 while the aggregate swings
     57-73 %, so the +-6 pp wobble is intensity variation WITHIN the fast state, a
     different phenomenon from the collapse.

CONSEQUENCE. "Utilisation collapses" has been the wrong mental model all along. Nothing
slows down: a discrete set of groups switches state, and stays switched. That reframes
the target -- the question is not "why is the fabric slower after the p-boundary" but
"what tips a group from the 85 % state into the 25 % state, and why is it irreversible".

The MSHR-bistability hypothesis fits: bypassed requests do not merge, so they generate
more traffic, fill more ways, and cause more bypasses -- positive feedback with no
restoring force, which is exactly a one-way state change. TESTABLE with the per-group
bankfull_bypass / mshr_timeout counters, which tb_fpu_util.svh already maintains as
fu_bankfull_byp[NumGroups] and fu_mshr_timeout[NumGroups] and currently only SUMS.
Emitting them per group (same one-line change as [FPUG]) would show directly whether
the 21 are the groups with elevated bypass. Needs a rebuild, so not started.

CORRECTION to the entry above. I recorded "groups join the slow state and never leave

WHY IT MATTERS FOR THE MECHANISM. Partial reversibility constrains the MSHR-bistability

marginal ones fall back once the spike passes, while the 21 that were already slow before
any boundary stay slow. So the tipping point is load-dependent, not absolute -- which
also explains why the slow-set SIZE differs by config (FGIR2 9, FG511 21, FG255 35):
different configs sit at different distances from the same threshold.

Utilisation tracks the count inversely throughout, as the two-state model predicts.

## Per-core throughput is invariant to fleet size (2026-08-09)

TESTE finished — the campaign's second completed run and the first at full load. Put
next to QTR, the pair answers the question QTR was built to ask.

    run     active cores   per-core work   benchmark cycles   whole-kernel util
    QTR         256        8 rows x 128     801,743           4.40% fleet / 17.60% per active core
    TESTE      1024        8 rows x 128     801,263           17.66%

Both print the identical per-core tile bounds — `N, P, m_start, m_end, p_start, p_end
= 512, 512, 0, 8, 0, 128` — so a core does byte-identical work in the two runs. The
completion times differ by **0.06%**, and the quarter-load run is the marginally
*slower* of the two.

QTR injects a quarter of the traffic into the same fabric. If aggregate NoC load were
what limits per-core rate, QTR should have finished substantially sooner. It did not.
**Aggregate injected load is not the limiter.**

Two things stop this from being explained away:

- QTR is not handicapped by its group selection. Its active set is groups 0–15 =
  mesh rows 0–1. In the equivalent full-load run at the same hardware config (FG511),
  those sixteen groups are the *fastest* sixteen of the sixty-four: mean util 83.6% vs
  59.4% for the other forty-eight, and only **1 of the 21 slow groups** falls inside
  them. QTR drew a near-optimal subset and still gained nothing.
- The control is the right one for a bandwidth question. Because the L1 interleave is
  hardware, QTR's sixteen active groups still fetch three quarters of their data from
  groups with no active cores. Remote distance is unchanged; only load is cut.

What QTR therefore does *not* test is locality — every remote hop it makes is as long
as before. A locality-limited explanation survives this experiment; a
bandwidth-limited one does not.

**Consistency with the plateau/tail anticorrelation.** The two runs reach the same
total by opposite routes: QTR holds a 65.3% per-core plateau and then sits in a ~7%
straggler tail for 200k+ cycles; TESTE holds 36.5% and tails off sooner. Plateau and
tail trade off almost exactly, which is the r = −0.89 anticorrelation showing up in
total runtime rather than in per-period util. It is the strongest evidence yet that
the sweep's plateau ranking does not predict throughput.

n = 2. Both completed runs, but only two, and VCS11 (test A at full load) is the third
and would test whether the invariance holds at a different plateau level.

## core_spread is a slow-set proxy — and says the cause is INSIDE the group (2026-08-09)

`core_spread=avg/max(gN)` (tb_fpu_util.svh:254-271, "PROBE 2") is **intra-group**: for
each group, its busiest core's FPU lane-cycles minus its idlest, that period;
`core_spread_g` is the group with the largest such *internal* spread. It is not a
measure of group slowness — a uniformly slow group has spread ~0 and is never flagged —
so testing it against the slow set is not circular.

Over every period of each per-group arm, how often the core_spread-max group is a
member of that arm's own slow set:

    arm      slow  samples  observed  expected      z
    FG255      44      109       70%       69%   +0.2    <- unimodal, no real slow set
    FG511      26       81       60%       41%   +3.6
    FG1023     13       39       54%       20%   +5.2
    FGIR2       8       49       37%       12%   +5.1
    FGGB0       4       37       30%        6%   +5.9

**3-5x enrichment in every bimodal arm, and correctly flat in the unimodal one.** FG255
is the control that makes this credible: where there is no slow set, the proxy finds
nothing, rather than manufacturing a signal.

**What it implies about the mechanism.** Slow groups are not uniformly slow inside;
they hold a mix of running and stalled cores. An external per-group throttle would slow
all sixteen cores together and produce spread ~0. So the binding constraint acts
*within* the group — bank conflict, MSHR way capacity, tile-local arbitration are the
candidates — which is consistent with the source-side MSHR being where a group's own
sixteen cores contend.

**Why it is useful — and the correction to how useful.** A first pass here claimed
`core_spread` is printed by all 46 arms and therefore gives per-group diagnostics
everywhere with no rebuild. That is wrong. PROBE 2 is a recent TB addition: **13 of 53
logs carry it**, and five of those are the `[FPUG]` arms that already have real
per-group data. So the proxy extends coverage to **8 additional arms** — BREMAP2,
IHASH0, IREMAP2, PA511, PA1023, PC1023, PD1023, PGB0 — all of them recent probe or
inter-group builds. Useful, and free, but a fraction of the fleet rather than all of it.
It does not supersede a rebuild for the 40 older arms; it only means the 8 newest do not
need one.

**Strength, stated honestly.** Absolute hit rate is 30-60% and only one group is named
per period, so this is an aggregate signal, not a classifier. It ranks; it does not
label. And the slow set it was validated against comes from the same run's `[FPUG]`
data, so the validation covers five arms — applying it to the other 41 is extrapolation,
justified by the consistency across four different configs but not directly checked
there.

**Also worth flagging:** v10 was never in the ranking's visible top tier, and the two

right about the 255 family for the wrong reason — it scores them well on equal-N

### The ranking structurally excludes fast arms (2026-08-09)

    arm    periods     cycles   >= N?   ranked
    v10        557    557,963      NO      —     <- the FASTEST arm in the campaign
    E          801    801,263     yes      7
    QTR        801    801,743     yes      —     (quarter load, excluded by design)
    A          865    866,235     yes      3

The equal-N ranking admits only arms with at least N periods. N is currently **591**.
v10 finished in **557**, so **the fastest arm in the campaign cannot appear in the
ranking at all** — not because it scored badly, but because it finished before
accumulating the window.

This is survivorship bias in the measurement, and it substantially explains the
inversion documented above. The ranking's candidate pool is filtered to arms slow enough
to still be running at period N, and **N ratchets upward as the campaign proceeds**, so
the filter tightens over time. An arm is, in effect, rewarded for lasting long enough to
be measured.

An arm that completed in fewer than N periods is not missing data — it finished early,
which is the best available outcome — yet the pool treats it identically to an arm with
no data. The dashboard now carries this as a first-class warning above the ranking table
rather than as a footnote, and lists any completed-but-unranked arms by name.

**Consequence for reading every earlier ranking in this document:** the pool was always
filtered this way, so historical ranking snapshots understate fast arms in proportion to
how fast they were. Rankings recorded before today should be read with that in mind.

### COLDSTART is worth 0.5% — a correction

Both halves of the pair have now completed (hold 255, `rd0+rdwr2`/2resp, coldstart the
only difference):

    v8  COLDSTART=0   658,216 cycles   plateau 26.2%
    v9  COLDSTART=1   661,490 cycles   plateau 26.3%   -> cs=1 is +0.50% slower

**0.50% is not a meaningful effect**, and an earlier version of this section over-read it.
On a one-sided bound just 3 periods past v8's completion, it claimed "cs=0 beats cs=1",
that this "supports COLDSTART=0 contributing to v10's 43.6% win", and that it
"contradicts the standing guidance" to keep `COLDSTART_GROUP_SYNC=1`. All three go too
far: a 0.5% effect cannot explain a 43.6% margin, and the standing guidance already
recorded "~1% at 8x8", which the measurement confirms rather than contradicts.

**What it actually establishes, and it is useful:** coldstart is nearly free at 8x8, so
**v10's advantage comes from the hold window and/or channel config, not from coldstart**.
That removes one of the three confounds in v10's result without spending another run.

**Method lesson.** A one-sided bound establishes an ordering, not a magnitude. It is
sound for "arm X is slower than a completion" and unsound for reasoning about causes.
Wait for the pair to finish before attributing anything to the variable.

### Over-read: the withdrawal was correct, and then some

Across six completions the work-done over-read now spans **+6.2% to +18.8%** — a 12.6 pp
band, up from the 5.5 pp quoted when it was withdrawn and the 0.3 pp claimed at n=2. Every

## The barrier-ablation test resolves: intra-group drift diverges 3.8 sd (2026-08-09)

FGGB0 (`GBAR_PLOOP=0`) vs FG511, offset-aligned, ten periods past the 44,000 threshold:

    window              n   d_intra  d_intramax   d_inter   d_util
    pre-barrier  <44k  43     -4.6        -4.1     -174.7     +9.8
    post-barrier >=44k 10    -15.6       +54.2     -424.6    +16.5

    baseline -4.6 (sd 2.9) -> post -15.6    shift -11.0 = 3.8 sd
    raw post deltas: -12 -17 -17 -17 -20 -18 -16 -11 -15 -13

**Every one of the ten post-threshold periods sits below the pre-barrier range** — the
divergence is not one outlier carrying a mean. The test as originally specified ("does
intra diverge beyond its measured baseline after offset 44,000") passes.

**Interpretation.** Removing the p-loop barrier lets cores within a group drift apart:
mean intra-group drift goes from -4.6 to -15.6, and `d_intramax` flips sign to **+54.2**,
i.e. the worst group's internal spread grows sharply. The barrier is doing real work
holding cores together. Ablation buys +16.5 pp of utilisation by letting groups run
unsynchronised, and pays for it in internal spread.

**This connects to the core_spread proxy result.** `core_spread` (intra-group
busiest-minus-idlest) is 3-5x enriched for slow-set membership, and the barrier directly
controls that quantity. So the barrier is a lever on the mechanism behind the slow set,
not merely on the aggregate number.

**It still does not say ablation is faster.** GBAR0's +16.8 pp mid-window decays to
-4.8 pp past 300k, and GBAR0 is at bench 471 against A's completed 866,235. That
comparison settles throughput and remains open.

**A near-miss worth recording.** An earlier attempt ran this test at n_post = **1** and
printed the same verdict — but the shift was -7.4 driven entirely by a single transition
period that also showed a +42.5 pp util jump. Right answer, no evidence. The verdict was
withdrawn at the time and only re-issued at n_post = 10. A one-period window is not a
window.
