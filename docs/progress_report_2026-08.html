1 Motivation

TeraNoC scales MemPool's shared-L1 programming model past the point where a flat logarithmic crossbar is physically realizable. Cores keep an all-to-all view of TCDM, but beyond a few hundred cores the interconnect must become a network — and remote load traffic becomes the scaling bottleneck.

Two mechanisms address that bottleneck, and both are the subject of this work:

  • Group MSHR coalescing. Under matmul traffic, many cores in a group load the same lines (the shared B operand). A per-group MSHR merges those outstanding remote loads into one NoC request and multicasts the single returned line back to every requester — cutting request pressure and redundant response bandwidth.
  • Spatz VLSU burst support. The vector LSU splits aligned unit-stride loads into 16-word bursts, converting many single-word remote requests into a few burst requests that the MSHR can coalesce efficiently.

The MSHR's behaviour is governed by roughly a dozen parameters — how many subscribers an entry waits for, how long it holds, how addresses map to banks. These are derived per GEMM shape by gemm_autotune.py from the kernel's sharing structure. That derivation is where the defect described in §4.1 lived.

2 Architecture

2.1 Interconnect

Intra-group traffic uses a combinational logarithmic crossbar for low-latency local sharing. Inter-group traffic uses a 2D mesh of narrow 32-bit FlooNoC routers. The hybrid keeps local access cheap while making global traffic physically scalable.

2.2 Group MSHR

Each group has 64 MSHR entries in banks of 4 ways. A (target_group, address) key selects a bank by XOR-folding address bits above the burst-align boundary, which keeps all beats of one burst in a single bank. Each entry holds the merge key, the burst length, and a per-requester record array indexed by merge slot.

Two parameters govern coalescing and are central to the results below:

  • hold_subs_burst / hold_subs_single — how many subscribers an entry waits for before issuing. Set from the kernel's sharing degree.
  • hold_window_* — how long it waits for them, backstopped by serve_timeout.

A shared prescaler divides the hold-counter tick rate by 16, so counters store windows in ticks rather than cycles. It is phased per entry (entry e ticks when the prescaler equals e's low bits) rather than pulsed globally — a global pulse would release up to 64 held fetches into the NoC in the same cycle, and this design is measurably sensitive to that bunching.

2.3 Runtime MSHR configuration new

Every knob comparison previously cost an RTL rebuild plus a full sweep. A CSR file per group now makes nine MSHR parameters software-writable at runtime, reached through the existing group barrier address window rather than a new address space. The MSHR ships disabled and software programs and enables it before the timed region.

Beyond experiment turnaround, this has a structural consequence used throughout this work: under runtime configuration the software-written value wins over the elaborated one for every per-shape parameter except merge_reqs, which sizes the record array. Shapes sharing a merge_reqs can therefore run on a bit-identical simulator — 23 builds collapse to 3.

3 Method

All results are cycle counts from VCS 2024.09 simulation of the full 256-core cluster, over 23 GEMM shapes spanning 2,048 to 131,072 ideal cycles.

Efficiency metric

Efficiency is ideal / actual, where ideal = M·N·P / 1024 — the roofline for 1024 FPU lanes. The testbench also emits a raw utilisation counter, but it measures lane occupancy and is not conserved across runs of identical work; it has previously inverted a real ranking in this campaign, so it is not used for comparisons.

Comparison discipline

Each sweep differs from its reference by exactly one knob, and every arm gates on a full define-set diff against that reference before it runs — any difference beyond the knob under test aborts the arm. This was added after configuration drift produced invalid results twice.

Why a cycle win alone is not accepted

A configuration bug earlier in this campaign produced a spurious 43% "improvement" by silently discarding work. Every result below is therefore checked against FPU busy lane-cycles and the MSHR's own request counters: a genuine speedup retires the same work in fewer cycles, and that is verified per arm rather than assumed.

4 Results

4.1 The autotuner clamp fixed & verified

For the four 128×N×512 shapes the autotuner derives a B-sharing degree of 1 — B is private to each core, so a second requester for a burst line can never arrive. The correct MSHR setting is therefore "do not hold burst entries at all". But an elaboration check required hold_subs ≥ 2, so the autotuner clamped the derived 1 up to 2.

The consequence, visible in the MSHR counters: those shapes allocated 61,344 / 122,721 / 245,540 / 491,216 burst entries respectively — doubling with N — and merged exactly zero of them. Every allocation was pure added latency on a load that was going to miss anyway.

The guard was relaxed to admit 1, which the RTL already defines as "bypass this class entirely", and the clamp removed from the autotuner so the derived value is emitted directly.

Each arm was verified against the lost-work failure mode: FPU busy lane-cycles match to within 0.5% and the single-request path to within 0.1%, so the same work retires in fewer cycles. Before the fix these four shapes were the campaign's entire net regression against the pre-campaign baseline; after it, all four sit at or below baseline.

The benefit does not decay with N, which the first two arms had suggested it would. Because the wasted allocation count scales with the work, so does the saving.

4.2 Runtime MSHR configuration feasibility established

Across all 23 shapes the runtime CSR costs a median +0.77%, with 18 of 23 under +5%. Five shapes were outliers — and four of those five were the same B-share=1 family, where the clamp was inflating an already-wasted allocation.

Re-running those four with the corrected parameter, on the same simulator binary so that the software-written CSR value was the only variable, removes the penalty entirely:

4.3 Shipping-configuration sweep 18 / 23 in flight

A methodological gap surfaced late: every one of the ~190 arms run to date pinned hold_prescale_w = 0 for cycle-accurate one-knob deltas, but the shipping default is 4. No arm had ever measured the configuration that actually ships. Two sweeps now do — dflt at pure flavour defaults, and latest adding the runtime CSR.

4.4 The hold prescaler

The prescaler is a backend PPA lever, not a performance feature. It narrows the per-entry hold counter from 11 bits to 7 — removing 4,096 flops at 4×4 and 16,384 at 8×8 — cuts that field's switching activity 16×, and shortens the comparator feeding the per-entry issue decision.

Its frontend cost, measured for the first time here across 16 shapes: mean −0.44%, median +0.49%, range −8.30% to +3.12%. The mean sits near zero but the spread does not — one shape gains 8.3%. Coarsening when an entry releases interacts with traffic patterns and can land either way, so this should be read as roughly-zero-mean per-shape noise rather than a flat tax.

5 Verification

Static analysis. A Spyglass lint of the current shipping configuration reports 9 errors, identical in count and location to the previous clean run, all in vendored Spatz/Snitch IP and all of the known-false read but never set class. Zero findings in project RTL. The lint was gated to confirm the newly-legal bypass parameter and both new Spatz defaults were actually present in the compile line — the flow otherwise exits successfully even when it has checked nothing.

Functional. Each result is corroborated by MSHR request-class counters and FPU busy lane-cycles, as described in §3. The runtime-CSR arms additionally reject any run where the MSHR was not confirmed enabled in all 16 groups, since an unconfigured MSHR does not fail — it silently measures a bypassed one.

6 Open items

open  512×256×512 under runtime configuration

This shape showed +252.7% under the runtime CSR at hold_prescale_w = 0. It has a B-sharing degree of 4 — its burst entries genuinely merge — so the bypass fix does not apply and it is the one regression still unexplained.

An interactive full-waveform run of the same shape at the shipping prescale completed cleanly at ~79,127 cycles, matching the healthy reference within 0.7%, which suggests the regression may be specific to a configuration that does not ship. Two batch arms are in flight to confirm this on a matched binary; neither has yet reached the point where the original arm diverged.

open  Synthesis guard coverage

44 ifndef TARGET_SYNTHESIS guards across six RTL files exclude verification-only state from synthesis — 64 bits per MSHR entry, or 65,536 flops at 4×4 and 262,144 at 8×8. That macro is defined by nothing in this repository; it relies on the backend flow invoking Bender with the synthesis target. This is very likely correct by convention, but it is unverified here and worth one confirmation, since the cost of it being wrong is a quarter of a million flops.
