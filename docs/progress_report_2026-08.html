1 Motivation

TeraNoC scales MemPool's shared-L1 programming model past the point where a flat logarithmic crossbar is physically realizable. Cores keep an all-to-all view of TCDM, but beyond a few hundred cores the interconnect must become a network — and remote load traffic becomes the scaling bottleneck.

Two mechanisms address that bottleneck, and both are the subject of this work:

  • Group MSHR coalescing. Under matmul traffic, many cores in a group load the same lines (the shared B operand). A per-group MSHR merges those outstanding remote loads into one NoC request and multicasts the single returned line back to every requester — cutting request pressure and redundant response bandwidth.
  • Spatz VLSU burst support. The vector LSU splits aligned unit-stride loads into 16-word bursts, converting many single-word remote requests into a few burst requests that the MSHR can coalesce efficiently.

The MSHR's behaviour is governed by roughly a dozen parameters — how many subscribers an entry waits for, how long it holds, how addresses map to banks. These are derived per GEMM shape by gemm_autotune.py from the kernel's sharing structure. That derivation is where the defect described in §4.1 lived.

1.1 Why matmul creates sharing — the general reason

Start from one fact about the operation itself, with no reference to how we wrote it:

To compute one output element C[m][p] a core must read an entire row of A (row m) and an entire column of B (column p).

So two cores computing different outputs in the same row of C read exactly the same row of A. Two cores in the same column of C read exactly the same column of B. The sharing is not a coincidence of our tiling — it is forced by which index each operand depends on.

Lay four cores out as a 2 × 2 block of the output and it is immediate:

                    B col p0        B col p1
                  +-----------+   +-----------+
   A row m0  ---> |  core 0   |   |  core 1   |   both read A row m0
                  +-----------+   +-----------+
   A row m1  ---> |  core 2   |   |  core 3   |   both read A row m1
                  +-----------+   +-----------+
                        |               |
                  core 0 & 2       core 1 & 3
                  read B col p0    read B col p1

   4 cores, but only 2 distinct A rows + 2 distinct B columns are needed.
   8 loads collapse to 4.

The general statement follows directly. Arrange p cores as a p₁ × p₂ grid over a block of the output:

  • each A row is read by the p₂ cores across its grid row,
  • each B column is read by the p₁ cores down its grid column.

The sharing degree is simply the width of the grid in the other direction. Scale the grid up and the sharing scales with it — which is exactly why the opportunity grows as the machine gets bigger, rather than washing out.

This is well-trodden ground, which is the point

Classical distributed matmul algorithms — Cannon (1969), SUMMA (van de Geijn & Watts, 1997) — are built on exactly this 2-D grid structure, and they turn it into an explicit broadcast along grid rows and columns. The matmul communication lower bounds (Hong & Kung, 1981; Irony, Toledo & Tiskin, 2004) have their shape for the same reason. An implementation that does not exploit the 2-D sharing simply moves more data than it has to.

What is different in a shared-L1 machine

In SUMMA the broadcast is written into the algorithm: the program explicitly sends a panel of A to every processor in a grid row before each update step. Here there is no broadcast to write — every core just issues an ordinary load for the address it needs. The sharing still exists, but it is hidden in the address stream rather than expressed in the program.

The group MSHR's job is to notice it. Loads that happen to target the same line get merged into one request, and the single reply is multicast back to everyone who asked. The machine ends up with SUMMA's communication pattern without the programmer arranging it — and when the sharing is not there, the same hardware quietly behaves like ordinary loads.

How to split the cores: not the obvious way

If both operands cost the same to fetch, the best grid is square — split the cores evenly and both sharing degrees are √p. That is the textbook answer, and here it is wrong.

A and B do not cost the same. A is read by scalar loads, one word at a time; B is read by the vector unit in 16-word bursts. Measured over a run, A generates about four times as many requests as B. Since coalescing saves a request every time one is shared, the operand that issues more requests deserves the larger sharing degree.

Making that precise — minimise total requests wA/sA + wB/sB subject to sA·sB = p — gives a simple rule:

s_A : s_B   =   w_A : w_B

   "share each operand as many ways as it generates traffic"

With 16 cores and 4:1 traffic that means s_A = 8, s_B = 2 — a 2 × 8 grid, not the square 4 × 4. The prediction holds against every shape measured:

1.2 The same structure in this kernel

The opportunity is not incidental to matmul — it falls directly out of how the kernel splits work. Each group receives a slab of the output matrix and divides its 16 cores into a two-dimensional grid. For a 512×512×512 GEMM on the 4×4 mesh:

dim_group = M / num_groups          = 512/16 = 32   rows of C per group
split_m   = dim_group / KERNEL_SIZE = 32/8   =  4   m-blocks
split_p   = cores_per_group / split_m = 16/4 =  4   p-slices
                                              -> a 4 x 4 grid of cores

Now consider what a core loads to compute C[m][p] = Σn A[m][n]·B[n][p]:

  • A[m][n] depends on m, not p. The four cores across one m-block row differ only in their p-slice, so they all need the same A element.
  • B[n][p..p+VL] depends on p, not m. The four cores down one p-slice column differ only in their m-block, so they all need the same B line.

So at any step the group's 16 cores need only 4 distinct A elements and 4 distinct B lines between them:

without coalescing:  16 A + 16 B = 32 requests cross the mesh
with coalescing   :   4 A +  4 B =  8 requests cross the mesh

The sharing is confined to a group because the work split is confined to a group. Cores in different groups work on different slabs of C and share almost nothing. That is the argument for placing the coalescer at group level: a per-tile MSHR would see only a fraction of each sharing set, and a global one would pay cross-mesh latency to capture sharing that does not exist there.

The model is predictive, not descriptive

Both sharing degrees follow from (M, N, P) before anything runs. The hardware hits them exactly — the measured merge ratio equals the predicted degree on every shape checked:

Note that the two degrees invert with M: at M=128 the A operand is shared 16 ways while B is private to each core; at M=512 both are 4. That inversion is exactly what §4.1 is about — the parameter derivation clamped B's true degree of 1 up to 2, so the hardware waited for a second requester that provably could not exist. The B measured = 1.0 on 128×1024×512 is that defect visible as a single number.

2 Architecture

2.1 Interconnect

Intra-group traffic uses a combinational logarithmic crossbar for low-latency local sharing. Inter-group traffic uses a 2D mesh of narrow 32-bit FlooNoC routers. The hybrid keeps local access cheap while making global traffic physically scalable.

2.2 Group MSHR

Each group has 64 MSHR entries in banks of 4 ways. A (target_group, address) key selects a bank by XOR-folding address bits above the burst-align boundary, which keeps all beats of one burst in a single bank. Each entry holds the merge key, the burst length, and a per-requester record array indexed by merge slot.

Two parameters govern coalescing and are central to the results below:

  • hold_subs_burst / hold_subs_single — how many subscribers an entry waits for before issuing. Set from the kernel's sharing degree.
  • hold_window_* — how long it waits for them, backstopped by serve_timeout.

A shared prescaler divides the hold-counter tick rate by 16, so counters store windows in ticks rather than cycles. It is phased per entry (entry e ticks when the prescaler equals e's low bits) rather than pulsed globally — a global pulse would release up to 64 held fetches into the NoC in the same cycle, and this design is measurably sensitive to that bunching.

2.3 Runtime MSHR configuration new

Every knob comparison previously cost an RTL rebuild plus a full sweep. A CSR file per group now makes nine MSHR parameters software-writable at runtime, reached through the existing group barrier address window rather than a new address space. The MSHR ships disabled and software programs and enables it before the timed region.

Beyond experiment turnaround, this has a structural consequence used throughout this work: under runtime configuration the software-written value wins over the elaborated one for every per-shape parameter except merge_reqs, which sizes the record array. Shapes sharing a merge_reqs can therefore run on a bit-identical simulator — 23 builds collapse to 3.

3 Method

All results are cycle counts from VCS 2024.09 simulation of the full 256-core cluster, over 23 GEMM shapes spanning 2,048 to 131,072 ideal cycles.

Efficiency metric

Efficiency is ideal / actual, where ideal = M·N·P / 1024 — the roofline for 1024 FPU lanes. The testbench also emits a raw utilisation counter, but it measures lane occupancy and is not conserved across runs of identical work; it has previously inverted a real ranking in this campaign, so it is not used for comparisons.

Comparison discipline

Each sweep differs from its reference by exactly one knob, and every arm gates on a full define-set diff against that reference before it runs — any difference beyond the knob under test aborts the arm. This was added after configuration drift produced invalid results twice.

Why a cycle win alone is not accepted

A configuration bug earlier in this campaign produced a spurious 43% "improvement" by silently discarding work. Every result below is therefore checked against FPU busy lane-cycles and the MSHR's own request counters: a genuine speedup retires the same work in fewer cycles, and that is verified per arm rather than assumed.

4 Results

4.1 The autotuner clamp fixed & verified

For the four 128×N×512 shapes the autotuner derives a B-sharing degree of 1 — B is private to each core, so a second requester for a burst line can never arrive. The correct MSHR setting is therefore "do not hold burst entries at all". But an elaboration check required hold_subs ≥ 2, so the autotuner clamped the derived 1 up to 2.

The consequence, visible in the MSHR counters: those shapes allocated 61,344 / 122,721 / 245,540 / 491,216 burst entries respectively — doubling with N — and merged exactly zero of them. Every allocation was pure added latency on a load that was going to miss anyway.

The guard was relaxed to admit 1, which the RTL already defines as "bypass this class entirely", and the clamp removed from the autotuner so the derived value is emitted directly.

Before the fix these four shapes were the campaign's entire net regression against the pre-campaign baseline; after it, all four sit at or below baseline.

The benefit does not decay with N, which the first two arms had suggested it would. Because the wasted allocation count scales with the work, so does the saving.

4.2 Runtime MSHR configuration feasibility established

Across all 23 shapes the runtime CSR costs a median +0.77%, with 18 of 23 under +5%. Five shapes were outliers — and four of those five were the same B-share=1 family, where the clamp was inflating an already-wasted allocation.

Re-running those four with the corrected parameter, on the same simulator binary so that the software-written CSR value was the only variable, removes the penalty entirely:

The fifth outlier, and the last one open

One shape resisted that explanation: 512×256×512 at +252.7%, with a B-sharing degree of 4 — its burst entries do merge, so bypass does not apply.

It turns out not to be a property of the runtime CSR at all. Re-running the identical configuration and ELF with only hold_prescale_w changed from the campaign's pinned 0 to the shipping default of 4:

The leading indicator was per-group minimum utilisation, not the aggregate. At the same point in the run the collapsing arm still reported 90–92% aggregate while its slowest group oscillated between 1.5% and 13% for thousands of cycles; the healthy arm held 90–96% throughout. A mean over 16 groups hides this entirely — which is why the per-group view is instrumented separately.

4.4 The hold prescaler

The prescaler is a backend PPA lever, not a performance feature. It narrows the per-entry hold counter from 11 bits to 7 — removing 4,096 flops at 4×4 and 16,384 at 8×8 — cuts that field's switching activity 16×, and shortens the comparator feeding the per-entry issue decision.

Its frontend cost, measured for the first time here across 16 shapes: mean −0.44%, median +0.49%, range −8.30% to +3.12%. The mean sits near zero but the spread does not — one shape gains 8.3%. Coarsening when an entry releases interacts with traffic patterns and can land either way, so this should be read as roughly-zero-mean per-shape noise rather than a flat tax.

4.5 Scaling to 1024 cores measured

The design also runs at 8×8 / 64 groups / 1024 cores. The MSHR is instantiated per group, so scaling replicates it 64× rather than widening it — group_mshr_num stays at 64 entries per group at both mesh sizes, and the structure carries over unchanged.

A 26-arm sweep on shape 2048×512×512 (ideal = M·N·P / 4096 = 131,072 cycles at 4096 FPU lanes) reached a best of 169,073 cycles — 77.5% of roofline, across a 4.4× spread between best and worst configuration.

These numbers do not compare with the 4×4 results above

Different mesh, core count, lane count and GEMM shape. The 8×8 work is a separate campaign; it establishes that the mechanism scales and what limits it there, not a like-for-like efficiency comparison. Its build directories have since been reclaimed, so the record is recovered from the campaign's live artifact rather than re-derivable from logs.

Two findings from that campaign shape how the 8×8 result should be read:

  • The scaling loss is group alignment, not the MSHR. 21 of 64 groups are persistently slow — the same set early and late (r = 0.92), bimodal at ~82% and ~22%, and not contiguous on the mesh. At 4×4 the inter-group spread stays within a few percentage points under any configuration; at 8×8 it fans out far wider. That spread is the loss.
  • An inherited default cost 22–108%. The 8×8 base configuration shipped hold = 1023 to every arm, where the 4×4 production default was already 255. Several arms were slow because of that inheritance rather than the variable under test — the same class of defect as §4.1, found the same way.

A software defect also had to be fixed before any 8×8 measurement was meaningful: the group barrier hardcoded a word stride valid only at 16 groups, so at 64 groups every barrier operation addressed a word outside the barrier window and the synchronisation silently did nothing — no hang, no error. Repairing it was worth 14.1%.

5 Verification

Static analysis. A Spyglass lint of the current shipping configuration reports 9 errors, identical in count and location to the previous clean run, all in vendored Spatz/Snitch IP and all of the known-false read but never set class. Zero findings in project RTL. The lint was gated to confirm the newly-legal bypass parameter and both new Spatz defaults were actually present in the compile line — the flow otherwise exits successfully even when it has checked nothing.

Functional. Each result is corroborated by MSHR request-class counters and FPU busy lane-cycles, as described in §3. The runtime-CSR arms additionally reject any run where the MSHR was not confirmed enabled in all 16 groups, since an unconfigured MSHR does not fail — it silently measures a bypassed one.

6 Open items

resolved  512×256×512 under runtime configuration

This shape carried the campaign's last unexplained regression — +252.7% under the runtime CSR. It has a B-sharing degree of 4, so its burst entries genuinely merge and the §4.1 bypass fix does not apply.

It is now accounted for: the collapse is specific to hold_prescale_w = 0, a value pinned throughout the campaign for cycle-accurate one-knob comparisons and which nothing ships. Re-running the identical configuration and ELF at the shipping prescale_w = 4 gives 80,064 cycles — 3.51× faster than the collapsing arm and +0.52% against the healthy reference, with 1 dead period instead of 169. Three independent arms agree. Details in §4.2.

Characterised, not root-caused. This establishes the shipping configuration is unaffected; it does not explain what prescale_w = 0 and cfg_runtime = 1 do to each other on this shape. Roughly 190 earlier campaign arms ran at prescale_w = 0 and carry that latent behaviour, so the mechanism stays on the list.

open  Synthesis guard coverage

44 ifndef TARGET_SYNTHESIS guards across six RTL files exclude verification-only state from synthesis — 64 bits per MSHR entry, or 65,536 flops at 4×4 and 262,144 at 8×8. That macro is defined by nothing in this repository; it relies on the backend flow invoking Bender with the synthesis target. This is very likely correct by convention, but it is unverified here and worth one confirmation, since the cost of it being wrong is a quarter of a million flops.
