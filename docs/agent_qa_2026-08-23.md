## Q2 — Response-sink FIFO / NoC protocol deadlock

**Has it recurred since June? No — not under the 8×8 campaign's traffic.**

Evidence from the running 1024-core sweep (the largest configuration we have):

- **51 of 51 completed arms completed.** Campaign status reports `WEDGED 0` across 248 arms.
- **51 of 51 completed transcripts contain `[CMS WARN] STUCK_REQ`** — and they still completed.
  So CMS WARN is *not* a deadlock signal here: the instances are transient and early
  (`cyc=3000 ... age=1093`, i.e. a request stalled ~1.1k cycles during the cold start), which is
  what the >1000-cycle threshold is designed to surface. Do not read the warning count as
  evidence of the hazard.
- Current RTL still ships `SpillRespOut = 1` (`mempool_group_mshr.sv:82`), and
  `docs/teranoc_architecture.md:369` still lists the sink as open risk #1.

**Recommendation: do not build the FIFO. Document the evasion argument and add a targeted stress
test.**

Rationale: 6.9 MGE / ~806k FF is an enormous, permanent area cost against a hazard that has not
appeared in 51 full-scale runs, while the cheap mitigation (decoupled bank req-accept from
resp-inject, plus the spill registers) has held. But "we didn't hit it" is not a correctness
argument, and the campaign exercises **one** traffic class — GEMM through the MSHR coalescer — so
absence here is weak evidence about other patterns.

What to write into §5.5, replacing "open risk" with a bounded claim:
1. why the decoupling breaks the cyclic dependency for request/response traffic of this shape;
2. the traffic classes that would re-introduce it — sustained many-to-one response convergence
   that keeps every `(tile, resp-port)` backpressured while new requests keep arriving
   (all-to-one reductions, broadcast/gather phases, or anything that parks responses at a
   congested sink);
3. a directed stress test generating exactly that pattern, run in CI.

Build the FIFO only if that test deadlocks, or if a planned workload has that shape. That converts
an open-ended risk into a falsifiable one for the cost of a testbench rather than 6.9 MGE.

## Q3 — `cfg_runtime` 3–12× slowdown

**No root-cause progress since mid-August.** The last relevant commit is `95de41fb`
("512x256x512 resolved — the collapse is specific to `prescale_w=0`"), which bounded one shape's
collapse but left the mechanism open. Both backend configs still carry the TAPE-OUT PIN
`group_mshr_cfg_runtime := 0` (`terapool_spatz4_fpu_backend_{4x4,8x8}.mk`) while the base config
flipped to 1 on 2026-08-20. WORKLOG is explicit that the 8×8 sweep has **no `cfg_runtime=0`
control arm**, so "the CSR path is neither ruled in nor out".

**Cheapest isolating experiment.** The MSHR telemetry is identical between arms, so the cost is
outside it: either in the *core* (extra scalar CSR traffic on the issue path) or in *timing/skew*
(the CSR writes perturb when groups arrive at barriers). One matched pair on a single shape,
differing **only** in `cfg_runtime`, discriminates those two in one run:

1. **Per-group progress first** — `[FPUG]` busy per window. If the slowdown shows as *group
   spread* (some groups far behind), it is skew/barrier, not per-core cost. If every group slows
   uniformly, it is per-core.
2. **Then barrier** — `[GBAR]` arrivals vs releases and `bar_rel`. A `bar_rel` that is uniformly
   `+0` means the barrier never fired at all (this has silently happened before).
3. **Then VLSU** — `stall_raw` vs `stall_acc` from the Spatz per-core trace. `stall_raw` points at
   scalar RAW waits on the CSR reads; `stall_acc` points at the offload queue.
4. `[BP]`/`[LP]` only if 1–3 come back clean.

**Gate the pair on a full define-set diff before believing any number.** A hand-picked subset has
produced a fake +34% "regression" here before; and pin every knob that has changed default since
the older arm was built.

## Q5 — Bank-hash reservation

**Accept field-select-with-derived-shifts as final for this tape-out, and close §8 explicitly.**

Shipped: `hash=3` field-select, with `bank_shift_single` / `bank_shift_burst` derived per shape
(`software/runtime/mshr_cfg.h`). Note the config path has a hard ordering requirement — disable →
drain → bank hash → rest → enable — and silently sets `MSHR_STATUS_BANK_BUSY`, keeping the *old*
hash, if the MSHR is not empty. Any new caller must honour that or it will run on a stale hash.

The doc's "fold, don't field-select" conclusion is therefore contradicted by what shipped, and
§8's fold@64 vs field-select@32 comparison was never run. Rather than leave that open, record it
as *superseded by the shipped derivation*, with the evidence that the derived shifts separate
banks for the shapes in the sweep.

**One check worth doing before fp16 / KERNEL_SIZE changes at 8×8** — cheap, and not a sweep:
confirm the shift derivation is expressed in **words, not elements**. fp16 packs two elements per
32-bit word, so an element-indexed derivation shifts by one bit relative to the byte address and
would silently select the wrong field. I have **not** verified which one `mshr_cfg.h` uses; it is a
five-minute read of the derivation and worth doing before trusting the hash at fp16.

## Q8 — Drain2 second-slot hoist

**Already re-applied, and committed. Nothing to do.**

The premise is out of date. In `HEAD`, the drain2 selection site carries the hoist *and* an
in-line refutation of the revert (`hardware/src/mempool_group_mshr.sv`, at the `drain2_cand`
scan):

> An earlier revision of this comment claimed the hoist was UNSAFE here, on the grounds that "the
> loop CLEARS `beat_pending2` as it goes". It does not: the clear lives in the DRIVE loop, which is
> a SEPARATE (tile,port) loop that begins only after this select loop has closed. The select loop
> writes nothing this predicate reads, so all iterations see identical state. Verified by
> enumerating every left-hand side in the select loop body.

Confirmed committed (present in `HEAD`, not just the working tree; the only uncommitted delta in
that file is an unrelated 6-line `$display`).

What is hoisted: the entry-invariant terms (`drain2_sub_ready` / `_tile` / `_port`) and the
second-slot destination port, computed once outside the loops. The per-`(tile,port)` candidate
scan necessarily stays inside, because it selects *per port*. Relevant commits: `9ab3fcfd`
(Phase A scan-hoist elaboration relief), `4412949d` (hoist the port-independent half of the
head-beat drain test), `4c4526cd` and `22623fd2` (B1: head-beat sub-scan from hoisted vectors,
then mask + LSB-isolate for the drain2 arbiter).

So head-beat-only drain did **not** stay for PPA or timing reasons — the equivalence argument was
accepted and the change landed. If a machine-checked equivalence is still wanted, that is a
CI/formal task, not an RTL change.
