# Dataless ROB — design proposal and plan

**Status:** proposal, no RTL written. Written 2026-08-27 after the `vl`-ceiling experiment.
**Branch:** `zexin/rob32_partial_commit` (spatz), currently holding only the measurement knob
`SPATZ_VLSU_NO_VL_CEILING` at default 0.

---

## 1. The idea, in one line

**The VLSU reorder buffer stores DATA. It should store only BOOKKEEPING, and let responses land
directly in the vector register file — the way an out-of-order CPU lets its physical register file
absorb out-of-order completion while the ROB tracks only order.**

---

## 2. What the ROB is today — evidence

`hw/ip/spatz/src/reorder_buffer.sv`, in its own words:

> *"This generic module provides an interface through which responses can be read **in order**,
> despite being written **out of order**."*

Its storage:

```systemverilog
data_t [NumWords-1:0] mem_d, mem_q;      // DataWidth = ELEN = 32 b
logic  [NumWords-1:0] valid_d, valid_q;
id_t   read_pointer_q, write_pointer_q;  // a ring; id_o = write_pointer_q
```

Instantiated **once per memory port** (`spatz_vlsu.sv:363`), each `NumWords = NrOutstandingLoads`:

| dimension | value (this config) |
|---|---|
| `NrMemPorts` | 4 |
| `NumWords` | `NrOutstandingLoads` = 64 |
| `DataWidth` | `ELEN` = 32 b |
| **data flops** | **4 × 64 × 32 = 8,192 per core** |

The 32→64 step measured **+5,150 flops/core**, of which **+4,096 (~80%) is `mem_q` alone**
(`docs/spatz_rob64_h1_design_plan.md` §5.1). At 1024 cores that step is ~5.3 MFF.

### Why the data must be buffered today

The VRF write address is generated by a **counter**, not by the response id:

```systemverilog
// spatz_vlsu.sv:802
vd_vreg_addr  = (commit_insn_q.vd << clog2(NrWordsPerVector)) + burst_word_idx;
// :1075
assign burst_elem_idx = commit_counter_q[0] >> clog2(ELENB);
```

`commit_counter_q` advances as elements drain **in order**. So the ROB must hold every outstanding
response until the oldest arrives, and its depth is therefore forced to equal the number of
outstanding tags.

---

## 3. Why that does not scale

Three consequences follow from "buffer depth == tag count", and we have measured all three today:

1. **Area.** Growing the outstanding window costs 4 × depth × 32 flops of pure data storage.
2. **A `vl` ceiling.** `use_port0_burst_req` demands `vl <= NrOutstandingLoads * MemDataWidthB`
   (256 B at ROB64). Above it a load **silently leaves the burst path**. This is what forces the
   three-way squeeze on `KERNEL_SIZE` (slice floor down, burst ceiling up, merge share up) that the
   decode tile policy is stuck in for `I = 5,120 / 6,144 / 2,048`.
3. **The ceiling cannot simply be relaxed.** Measured 2026-08-27: with
   `SPATZ_VLSU_NO_VL_CEILING=1` the run dies at cycle 14,849 on assertion A4,
   `spatz_vlsu.sv:2026`, *"Block and single ROB id request asserted together"* — whose own comment
   says the ROB then *"serves the block and drops the single silently"*.
   See `spatz_vlsu_ceiling_analysis.md`.

And the thing the big ROB currently buys is narrow: measured **B vs C = +0.0%** (ROB64 and ROB32
give **bit-identical** cycle counts with dual-load off). All of ROB64's value is **H1 dual-load**,
worth **+16.4%** on the load-starved `p09` arm — because it is the only way to get two loads'
worth of tags outstanding.

**So: tags are what we want more of; data storage is what we are paying for.**

---

## 4. Proposal

Split the two roles the ROB currently fuses.

| role | today | proposed |
|---|---|---|
| **allocate a unique response tag** | ring pointer into the data array | free-list of ids, **cheap**, scale to 128/256 |
| **reorder responses** | hold data until in-order | **deleted** — write to VRF at the id's element offset |
| **rate-match 4 mem ports → 1 VRF write port** | same data array | **small FIFO (~8–16 entries), independent of tag count** |

### The enabler

Ids are allocated **sequentially per instruction** (`id_o = write_pointer_q`, incremented per
allocation), and requests are issued in element order. So for a load whose first tag is `first_id`:

```
element_offset = (response_id - first_id) mod NumIds
vrf_waddr      = (vd << clog2(NrWordsPerVector)) + f(element_offset)
```

i.e. the element position is **recoverable from the tag**, which is exactly the information the
counter reconstructs today by insisting on in-order drain. Store `first_id` per in-flight
instruction (a handful of bits × `NrParallelInstructions`) and the counter is no longer needed to
place data.

### What this buys

* Outstanding window becomes a function of **id count**, not flop count. 128 or 256 tags is a
  free-list and a wider id field, not 4 × depth × 32 flops.
* **The `vl` ceiling disappears as a concept** — there is no "one ROB batch" any more.
* `KERNEL_SIZE` is freed from the burst ceiling, leaving only the slice floor and merge share
  (see `qwen38_kernel_mapping.md` §5.6).
* Dual-load runahead becomes **unnecessary**: with enough tags, one instruction can hold what two
  co-resident instructions hold today. The +16.4% is obtained without H1's complexity.

## 5. What must be re-established (the hard parts)

These are the reasons the current design is the way it is. Each is a work item, not a detail.

### 5.1 Chaining — the biggest one

Chaining today is *implied* by in-order drain:

```systemverilog
// spatz_controller.sv:312 — "Enable the VRF port if the dependant instructions wrote in the
// previous cycle."
sb_port_ready_mask[port] = ~deps | wrote_result_q;
```

"Producer wrote last cycle" is safe **only because writes are monotonic in element order**, so a
consumer reading behind the write frontier can never read an unwritten element. Out-of-order writes
break that implication.

**Required:** a per-element (or per-VRF-word) valid frontier per in-flight instruction, and the
consumer gated on *its own* read index being below it. Cost is roughly `NrWordsPerVector` bits per
in-flight instruction — far below 8,192 flops, but it is new state **and it touches the chaining
path, which is load-bearing** (measured: chaining is what makes same-LMUL load/FMAC pairing cover
memory latency without dual-load).

### 5.2 The block allocator

`BlockAlloc` reserves a `MaxBurstWords` window in one cycle. Assertion A4 (block and single id
requested together) is what fired when the ceiling was relaxed. A free-list allocator must serve
block reservations and single ids from one structure without the mutual exclusion the ring gives
for free.

### 5.3 ParityDrain / `burst_odd_expected_q`

The MSHR pins beat *b* to response port `1 + (b&1)`, and the VLSU classifies with
`burst_odd_expected_q`, sized to `NrOutstandingLoads`. This assumes a known beat order. Out-of-order
landing needs the parity derived from the **tag**, not from arrival order.

### 5.4 Strided / indexed / `vstart != 0`

`vd_elem_id` uses `commit_counter_q` with a `vreg_start_0` correction for non-zero `vstart`, and
strided/indexed have irregular element→address maps. These ops are already on the
`prevent_chaining` list; simplest is to keep them on the legacy in-order path and apply the new
path only to unit-stride loads (which is where all the burst traffic is).

### 5.5 VRF write bandwidth

4 memory ports can return up to 4 words/cycle into **one** VLSU VRF write port, arbitrated against
VFU and VSLDU by a fixed-priority bank arbiter (`spatz_vrf.sv:89-112`, VFU > VLSU > VSLDU). The
rate-matching FIFO must absorb that burstiness; its depth is a bandwidth question, not a tag
question, and should be sized from measurement rather than guessed.

## 6. Staging plan

Every stage is independently testable and independently revertible. **No stage ships without its
gate.** Knobs default OFF so each stage's netlist is bit-identical until enabled.

| stage | change | gate |
|---|---|---|
| **S0** | Per-instruction `first_id` tracking + `element_offset` derivation, computed **in parallel** with the existing counter and only `assert`-compared. No behaviour change. | Assertion silent across the full `vector-burst-test` (15 cases) and one matmul arm. Proves the tag→element map is correct before anything depends on it. |
| **S1** | Per-element valid frontier, again computed and asserted against in-order drain. No behaviour change. | Frontier matches the counter on every cycle, all cases. |
| **S2** | Knob: VRF write address from `element_offset` instead of the counter, **still in-order drain**. Decouples addressing from ordering without changing timing. | Cycle-identical to baseline. Any delta is a bug. |
| **S3** | Knob: allow out-of-order drain (data still buffered). Chaining now uses the S1 frontier. | `vector-burst-test` PASS, matmul PASS, `[VLSU OVERSHOOT]` silent, cycle count within noise. |
| **S4** | Shrink the buffer below the tag count; add the free-list allocator; block reservation reworked. | A4 and the other `gen_block_alloc_asserts` silent; `vl > tags*4` now legal — the exact case that fails today. |
| **S5** | Raise tags to 128/256; re-measure the `p09`/`p78` spread against A/B/C. | Recovers H1's +16.4% without `dual_load`. |

**Fallback at every point:** `git checkout zexin/teranoc_burst` (mirrored at origin, `58c56d0`).

## 7. Validation assets that already exist

* `vector-burst-test` with the LMUL cases (m2/m4/m8, 128/256/384/512 B) — the directed test that
  found A4. Cases 10–14 are exactly the over-ceiling regime S4 must legalise.
* `[BURSTWHY]`, `BURST DROPPED`, `[VLSU OVERSHOOT]` probes (committed `58c56d0`).
* Images A/B/C/D at 8×8, define-diffed and orthogonal.
* The A/B/C arm set (10 shapes, 9%→78% utilisation) as the performance reference.

⚠️ **`CMS WARN` is not a failure signal for these tests.** The passing ROB32 baseline showed 1,477;
the failing relaxed run showed 508. Use the UART verdict and `$fatal`.

---

## 8. Open questions — to settle before S2

1. **Is the tag→element map exactly `(id - first_id) mod NumIds`?** S0 exists to prove it. It is an
   assumption, not yet a measurement; `vstart != 0` and the tail phase are where it would break.
2. **How deep must the rate-matching FIFO be?** Needs a measurement of response burstiness per port
   under real matmul traffic, not a guess.
3. **Does anything else read `rob_rdata` in order?** ParityDrain and the commit counters are known;
   a full consumer audit is part of S0.
4. **Is the VRF write port the real bottleneck at 128+ tags?** More outstanding words means more
   writes/cycle to absorb. If the single VLSU port saturates, the win is capped by the VRF, not the
   ROB — worth an early estimate, because it would change the target tag count.

---

## 9. Expected payoff

| | today (ROB64+H1) | proposed (128 tags, small FIFO) |
|---|---|---|
| data flops/core | 8,192 | ~2,048 (16-entry × 4 ports × 32 b) |
| outstanding window | 256 B | 512 B+ |
| `vl` ceiling | 256 B | none |
| legal `KERNEL_SIZE` | 8, 4 | 8, 4, 2, 1 |
| dual-load needed | yes (+16.4% on `p09`) | no |

**The honest summary:** the payoff is real but the work is in §5, not §4. The addressing change is
small; re-establishing chaining safely is not. S0–S2 are cheap and answer whether the premise holds
before any behaviour changes.
