## What was fixed

Two independent defects, both shipped 2026-09-01/02:

1. **MSHR bank hash** — `bank_burst_bits` is a 1-bit CSR, so software-derived 2/3/4 truncated to
   its LSB and the burst class reached 4 of 16 banks. Fixed by capping the derivation and lowering
   `BankShiftMin` 5→4 so the corrected shift is accepted rather than refused
   (`software/runtime/mshr_cfg.h`, `hardware/src/mempool_group_mshr_cfg.sv`).
2. **`SPATZ_1XVL_LOAD_LMUL`** — a 512 B burst load is 128 words and `rob_depth` is 128, so one
   load claims every ROB0 id and deadlocks before the kernel. Now derived from the shape with a
   build-time `#error` (commit `3bab8d8d`). See
   `memory/project_rob0_vl_ceiling_is_a_tag_bound.md`.

The arms in this table isolate **(1)** — same ELF shape, same define set, only the RTL parameter
and the derived CSR differ. The **(2)** arms are the `rf_` wave and have not landed yet.

## Result 1 — the fix RECOVERS every arm that previously produced nothing

Seven baselines never printed `execution took` at all: they sat in the RH livelock, riding out
`serve_timeout` on every remote load until the wall clock killed them, at 4–5 % utilisation.

| arm | baseline RH-STUCK | baseline result | corrected cycles | post RH | post util |
|---|---:|---|---:|---:|---:|
| `fp16_ks4_16x128x4096` | 41,807 | none | **6,996** | 16 | 68.47 % |
| `fp32_ks4_16x128x2048` | 30,345 | none | **7,789** | 8 | 63.89 % |
| `fp16_ks2_8x128x8192` | 16,343 | none | **7,798** | 16 | 72.04 % |
| `fp32_ks4_8x128x4096` | 14,044 | none | **6,349** | 16 | 73.33 % |
| `fp32_ks2_8x128x4096` | 10,940 | none | **8,102** | 16 | 70.11 % |
| `fp16_ks4_8x128x8192` | 10,795 | none | **5,866** | 16 | 78.45 % |
| `fp32_ks2_4x128x4096` | 4,116 | none | **6,387** | 16 | 45.24 % |

`fp16_ks2_4x128x8192` (baseline RH 2,170) is the eighth and is still running.

**RH drops to a flat floor of 8–16 regardless of how bad it was** — 41,807 and 4,116 both land at
16. That is a fixed residue, not a proportional one: a handful of hold episodes that never becomes
self-reinforcing. `resp_hold` and `cache_aged` are 0 on all seven.

**Predicate: B ∈ {4,8,16} at KS ∈ {2,4}** — fewest sharers per group, exactly where the truncated
`bank_burst_bits` left the MSHR reaching a quarter of its banks.

`fp32_ks2_4x128x4096` is the outlier at 45.24 % utilisation, the only recovered arm below 63 %.
Unexplained; it completes, which it never did before.

## Result 2 — on healthy baselines it is a null, with two exceptions

| arm | baseline | corrected | Δ |
|---|---:|---:|---:|
| `fp16_ks2_128x1024x512` | 84,083 | 83,299 | −0.93 % |
| `fp16_ks2_32x256x2048` | 38,179 | 38,293 | +0.30 % |
| `fp16_ks2_64x512x1024` | 51,675 | 51,612 | −0.12 % |
| `fp16_ks4_32x256x2048` | 20,896 | 20,746 | −0.72 % |
| `fp32_ks2_128x1024x256` | 84,710 | 85,105 | +0.47 % |
| `fp32_ks2_32x256x1024` | 38,339 | 38,447 | +0.28 % |
| `fp32_ks2_64x512x512` | 51,734 | 51,708 | −0.05 % |
| **`fp32_ks2_16x128x2048`** | 15,344 | 15,628 | **+1.85 %** |
| **`fp16_ks2_16x128x4096`** | 13,728 | 14,391 | **+4.83 %** |

**The prediction that healthy arms stay within ±1 % is FALSIFIED** on the two bolded rows.

Both are B=16, KS=2 — and both are *slower* with the corrected hash. Every stress counter is
zero on both sides (`RH=0`, `resp_hold=0`, `cache_aged=0`, `bankfull_bypass=0`), so this is not
a new stall; utilisation simply drops (56.17 → 47.82 % and 48.46 → 43.64 %). A bank hash that is
better *on average* can still be worse for a particular access pattern, and B=16/KS=2 appears to
be one. Not yet root-caused, and it should not be written off as noise: +4.83 % on a
13,728-cycle arm is 663 cycles, and the sibling shapes move by tens.

## How to judge this fix — and how NOT to

**Use RH-STUCK, not `bankfull_bypass`.** `bankfull_bypass` is **0 on all 44 4×4 baselines,
including the seven livelocked ones**. Surveying it produced two successive wrong conclusions
here (first "a throughput win is expected", then "there is nothing to recover"). The pressure
lives in the RH-STUCK episode count: single digits on healthy arms, 10⁴ on livelocked ones.

Generally: *a stress counter that is identically zero across a whole grid is a reason to distrust
the counter, not evidence of health* — especially when some arms in that grid produced no result
at all. Ask what signature the **resultless** arms carry first.
