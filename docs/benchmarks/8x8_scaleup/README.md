# 8x8 scale-up sweep — iso-work A-share ladder

**Dispatched** 2026-08-22 ~06:00 · **batch** see `batch.txt` · **status** running

## What this measures

How the group-MSHR coalescing design scales from the 4x4 mesh (256 cores / 16 groups) to
**8x8 (1024 cores / 64 groups)**, running the main-tree design: **idea-2 + bank-full
backpressure + the `cache_reuse_target` bit-width fix**.

The nine arms hold **total work `M*N*P` constant** and vary only **M**, which alone sets
`split_p` — how many cores share the same A rows, i.e. the A-share degree the group MSHR can
coalesce. Growing total size while holding M fixed would learn nothing about coalescing; this
ladder isolates it.

| rung | fp16 shape (work 1,073,741,824) | fp32 shape (work 536,870,912) | A-share |
|---|---|---|---|
| 1 | `512x2048x1024` | `512x1024x1024` | 16-way |
| 2 | `1024x2048x512` | `1024x1024x512` | 8-way |
| 3 | `2048x1024x512` | `2048x512x512` | 4-way |
| 4 | `4096x512x512` | `4096x256x512` | 2-way |
| 5 | `8192x256x512` | *(impossible — C alone needs 20.3 MiB > 14.5)* | 1-way |

The 1-way rung is **fp16-only**: at that M the C matrix (`M*P`) dominates and fp32 cannot fit L1.

## Configuration

```
hardware   image  hardware/build_vcs_8x8/mempool_simvopt   (VCS, elaborated once at build time)
           config terapool_spatz4_fpu_8x8   1024 cores / 64 groups / 16 tiles per group
           knobs  GROUP_MSHR_BANKFULL_BACKPRESSURE=1  MERGE_REQS=16  RESP_CACHE=1  CFG_RUNTIME=1
software   apps   sp-fp16-<shape> / sp-fp32-<shape>, generated by scripts/gen_gemm_shape_app.sh
           built  CONFIG=terapool_spatz4_fpu_8x8  MERGE_REQS=16  OUT_PREFIX=s8_
           define EXTRA_DEFINES="-DMATMUL_SPOTCHECK=1"   (self-check; costs 0 measured cycles)
           gated  NUM_CORES=1024  NUM_GROUPS=64  MSHR_CFG_BANKFULL_BP=1  MSHR_MERGE_REQS=16
fleet      badist, backend=vcs, --mem-gb 12   (measured peak 7.80 GiB)
```

**No `-DGROUP_BARRIER` and no `-DGBAR_PLOOP`** — the kernel defaults are `GROUP_BARRIER=0`
(per-step barrier, measured net-negative) and `GBAR_PLOOP=1`. An arm whose define set shows
`-DGROUP_BARRIER=1` is misconfigured, not an experiment.

## Read the results with these caveats

1. **DISPATCHED SPECULATIVELY.** Gate 6c step 2 was NOT met: no pilot had completed and no
   spotcheck had passed when these were launched. Every arm carries its own spotcheck, so
   correctness is self-reported per arm — **check it before quoting any cycle count**.
2. **L2 bandwidth per group HALVES at 8x8** (64 groups / 32 channels = 2:1, against 16/16 = 1:1
   at 4x4). Any cross-mesh loss mixes mesh scaling with this halving, and the ladder does not
   separate them. Do NOT report a scale-up loss as "the NoC does not scale".
3. **Record `RH` per arm, not just cycles.** `RH` gates whether backpressure can help a shape at
   all; two shapes with identical `bankfull_bypass` respond completely differently depending on
   whether the request-hold pathology is present.
4. **The M=128 family cannot run here.** `M % 512 == 0` at `kernel_size=8` excludes every
   `128x*` and `256x*` shape — including the ones that produced the largest 4x4 results
   (reuse-target 10.7-21x). They are not portable to 8x8 without changing `KERNEL_SIZE`, which
   changes LMUL and burst behaviour and would break comparability.

## Monitoring a multi-batch campaign

The sweep is dispatched as several badist batches (waves). Two traps make per-batch monitoring
wrong, and both have already produced false readings in this project:

1. **`badist status` with no argument reports the NEWEST batch only.** With 47 arms live across two
   batches it showed 38. A watcher that greps its output declares the other batch's arms missing.
2. **`fetch` also resolves exactly one batch** (`_resolve_batch`, newest by default). A bare `fetch`
   delivers the last wave and strands every earlier wave's transcripts on the workers.

Pinning a batch id in the watcher is not the fix either — ids multiply with each wave, so the
watcher silently stops covering the campaign the moment a new wave is dispatched.

**The stable key is the run-prefix on disk.** Every arm of every wave delivers to
`hardware/s8_<arm>/transcript`, batch-independent. `scripts/badist/campaign_status.py` joins the
248-arm manifest against every batch ledger that mentions one of our arms and reads results from
disk:

```sh
scripts/badist/campaign_status.py            # summary
scripts/badist/campaign_status.py --fetch    # fetch EVERY batch first, then summarise
scripts/badist/campaign_status.py --verbose  # + per-arm cycles/RH/util, fastest first
```

It classifies into `done / running / pending / not-dispatched / failed / WEDGED / no-probe`. The
last two exist because both failure modes **look like success**:

- **WEDGED** — cycles advance at full CPU but `util<0.5%` with a huge `CMS WARN` count. The cycle
  counter climbing is what makes a wedge read as a healthy slow run. (Two `pa2` arms sat like this.)
- **no-probe** — the arm completed and reported a cycle count, but emitted zero `[FPU]` lines, so
  there is nothing to measure. A completion count alone would score this as a success.

A watcher must emit on every terminal state, not just completion; silence is indistinguishable from
"still running".
